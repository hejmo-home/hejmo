## Context

ADR 0002 published V1.0 as pre-releases 0.x and called "release 1.0" the version after the V1.x items of ADR 0003. On 14/11/2026 the product owner settled the V1.x scope (grilling questions Q41–Q58) and decided that the first public version is really a 0.1, not a 1.0.

## Decision

### Versions

- **0.1** is the first public version: the V1.0 work packages 4–6 plus install guide, auto-update with rollback, resource and security measurement, stars, routines with templates, subtasks, VTODO export, passkeys and the MCP server.
- **0.2 and later:** Outlook sync, photo screensaver, brightness control, choosing people per display (free layouts).
- **V2:** box as CardDAV server (Hejmo has no address book in V1).
- **1.0** names a later version declared stable; not scheduled now.
- Until 0.1 the founding family runs preview builds from `main`; these are not releases.

### Hardware

- Development and the tests before 0.1 use an iPad and iPhone as normal screens; no Raspberry Pi and no E-Ink tablet are bought (map ticket #43 stays deferred).
- Functions that only an E-Ink device or the kiosk adapter can show (black-and-white on real E-Ink, ghosting reload, front light in quiet mode) are built and tested against a fake kiosk adapter and marked **experimental, not yet tested on E-Ink devices** in the install guide and release notes of 0.1.

### Install and auto-update

- **Install:** Docker Compose on any Linux, plus an install script for Raspberry Pi OS that sets up Docker and the box. No own operating system image.
- **Auto-update** (on by default): a small host-side script that the install script registers as a systemd timer. At 03:30 it fetches the newest **published** version (release tags without a pre-release suffix, never preview builds), backs up the database, restarts the box, waits for `/healthz`, and on failure returns to the previous image and database. The container gets no access to the Docker socket.
- Box and host script exchange settings and status only through two small files in the data volume (settings written by the box, status written by the script) with fixed keys and values; the script accepts nothing else from it and never runs or interpolates its content. The script itself is updated only by re-running the install script, never by auto-update.
- The script installs only images whose signature from the project's release workflow it has verified (cosign, keyless via GitHub OIDC), and records the previous image by digest for rollback.
- The database backup is taken with SQLite's online backup or with the box stopped, never by copying the live file. Settings offer "off" and "notify only"; after an update the web interface shows once what is new; after a rollback parents see a notice with the reason.

### Measurement

- CI runs `govulncheck`, `gosec` and a container image scan.
- Memory, CPU and start time are measured in CI on the arm64 runner in a container limited like a Raspberry Pi (1 CPU, 1 GB), with thresholds that fail the build. The install guide marks the Raspberry Pi as "tested in emulation" until confirmed on hardware.
- A documented threat model (home network, displays, phones, DNS records at deSEC) with the checks it leads to. No external penetration test before 0.1.

### Routines, stars, subtasks

- A **routine** is the ordered sequence of one person's tasks for a part of the day (e.g. Mia's morning). It has a name, a person, a part of the day (morning, after school or evening) and an ordered list of tasks. A task belongs to at most one routine; a task in a routine takes its part of the day from the routine, a task outside a routine keeps the optional morning or evening of ADR 0015. The personal view shows a routine's steps with large checkboxes.
- Details decided with the design of ticket 7.2 (#91, approved by the product owner on 15/11/2026): a person has at most one routine per part of the day; "after school" is a part of the day that exists only in routines (a task that leaves such a routine becomes an any-time task); dissolving a routine or taking a task out of it deletes no task, star or history; changing a routine's part of the day changes it for all its tasks; on the personal view a routine without a task due today is not shown, and its first open step is marked as the next one.
- The person column's progress bar (ADR 0016) counts all of the person's tasks for today, routine steps included; the family view shows no separate routine bar.
- **Routine templates:** the box ships templates in German and English (school-child morning, daycare-child morning, evening, after school; 4–6 steps each with emoji and star value). A parent picks a template, a person and the part of the day; the box creates an independent copy to adapt. Parents can save a routine as their own template. Sharing templates with other households comes in V2.
- **Stars:** every task has a star value (0 allowed). A new task's default is 1 for a child and 0 for an adult; parents can change it per task. Ticking off credits it, unticking deducts it; every booking goes into a star log. Parents can book stars by hand with a short note (e.g. "redeemed: ice cream"). Stars show only for people with at least one task worth stars or a star booking. Star bookings belong to the person, not to a household or membership, so linked households (V3) can share a child's star account. Reward catalogue, streaks and badges come in V2.
- **Subtasks:** items a task is split into, each ticked off on its own. Ticking the last open subtask completes the task and credits its stars; ticking the task itself ticks all its subtasks; unticking a subtask of a done task unticks the task. Stars belong to the task only.
- Details decided with the design of ticket 7.4 (#93, approved by the product owner on 15/11/2026): unticking the task itself unticks all its subtasks and deducts its stars (so "done = all subtasks done" always holds); the other subtasks stay ticked when one is unticked. Ticks belong to one occurrence of the task (a day) and start open again with the next one. A subtask added to a task that is done today counts as done for today, so nobody loses stars; removing the last open subtask completes the task and credits its stars. At most 10 subtasks per task, one level only; a subtask is a title with an optional emoji. Subtasks are edited on the task's own page. The person column's progress and the routine progress count tasks, not subtasks. Inside a routine the "next" marker moves to the first open subtask of the next task.

### VTODO export

- The box's CalDAV interface offers one task list per person. Parents' CalDAV clients see every list; access follows token scopes as in ADR 0012.
- Task lists need a device token with the token scope `tasks`; `calendars` alone does not open them. Tokens of a child are refused, as for calendars.
- From outside, title, notes (a new optional free-text field on a task), the date of a once-task and completion can be changed. For a repeating task the client sees today's occurrence; completing or un-completing it ticks or unticks that occurrence. Person, emoji, star value, routine, repetition and subtasks have no place in the client and keep their values in the box.
- Tasks are created only in Hejmo, because a task needs its person. Creating and deleting from outside are refused (403); the client shows the task again at its next sync.
- A completion from outside credits the stars exactly once; un-completing from outside deducts them like unticking.

### Passkeys

- Passkeys are an additional sign-in for adults that replaces password and one-time code at sign-in. The setup wizard offers to create one after the HTTPS step; password and one-time code stay as the way back.
- The relying-party ID is the name the box is served under (public name, or the own CA's DNS name such as `hejmo.local`); passkeys are offered only when the box is reached by that name, never by IP address. Changing the box's name makes existing passkeys unusable; the settings page says so, and password and one-time code keep working.
- A passkey counts as both factors: after a reset of one-time codes (ADR 0017) a passkey sign-in still works and asks to set up new one-time codes; confirming a reset of another parent's codes accepts a passkey instead of password and one-time code.
- Library: `go-webauthn/webauthn` (BSD-3-Clause), decided by the product owner as make-or-buy.

### MCP server

- Off by default. A parent switches it on and creates an API token with chosen token scopes for it. It offers the REST API's functions as MCP tools (events, lists, tasks, meal plan) and enforces the token's scopes unchanged. Only API tokens created for MCP work there; tokens of a child are refused; it is served only over HTTPS; managing tokens and settings is never offered as a tool. Routines, templates and star bookings fall under the `tasks` resource.
- Library: the official `modelcontextprotocol/go-sdk` (Apache-2.0, older contributions MIT; both compatible with AGPL-3.0), decided by the product owner as make-or-buy.

## Consequences

- New tickets for the 0.1 items; the V1.x section of ADR 0003 is replaced by this split.
- The data model for tasks grows by routines, templates, star bookings and subtasks; ADR 0015 already stored tasks so that VTODO needs no remodelling.
- The public promise "runs on a Raspberry Pi" rests on emulation until someone confirms it on hardware.

## Notes on passkeys (added in ticket #95)

- **Box name:** the public name when the box has one; with the own CA it is `hejmo.local`, which is on every own-CA certificate. A box that was set up under another LAN name (such as `fritz.box`) offers no passkey there; passkeys work under `hejmo.local`. A request counts as "by the box name" when it comes over HTTPS with that name as host; the origin the browser sends must match it, port included.
- **User verification is required** (`userVerification: required`, resident key required, no attestation). That is what lets one passkey count as password and one-time code; an authenticator that cannot verify the user cannot make a passkey for Hejmo.
- **The wizard offers the passkey after "Create account"**, not after the HTTPS step as the section above says: the account must exist first, and the one-time code follows.
- **Only a browser session creates a passkey**, never an API token or a paired phone's session (403), and not a browser session that only has its password after a reset of one-time codes (the new codes come first): a passkey signs in for good, so a stolen token must not be able to make one. Listing, renaming and removing work with tokens (scope `people`).
- **Confirming the reset of another parent's one-time codes** takes the acting parent's own passkey instead of password and code when they have one and the box is reached by its name; a passkey assertion for a fresh challenge is checked like a sign-in. Through the REST API the reset still takes password and code. The same step removes the passkeys of the other parent that the acting parent ticked (product owner Q9, 15/11/2026: listed with checkboxes, none ticked in advance).
- **The browser remembers one flag** (`hejmo_passkey_used`, no name, no secret) after a passkey sign-in; with it the passkey is the main action on the sign-in page of that device.
- **Ceremonies are held in memory** (two minutes and a half, once, bound to their kind and person); after a restart a ceremony is begun again.
- **"One-time codes" in Settings is now "My account"** (`/account`), as ADR 0017 names it: passkeys, one-time code with recovery codes, and one page per other parent for resetting their one-time codes (`/account/reset/{id}`). `/otp` redirects there.
- **Storage:** table `passkeys` (credential record as JSON, box name, device kind, last use); a session remembers the passkey it was made with; an account remembers who reset its codes and when.
- **Libraries:** go-webauthn/webauthn v0.18.2 (BSD-3-Clause) and what it needs: fxamacker/cbor (MIT), go-viper/mapstructure (MIT), go-webauthn/x (BSD-3-Clause), golang-jwt/jwt (MIT), google/go-tpm (Apache-2.0), tinylib/msgp (MIT), philhofer/fwd (MIT), x448/float16 (MIT).
