# 0025. Uploading an update file in offline mode

- Status: Accepted
- Date: 23/11/2026
- Amends: [0018](0018-path-to-0-1.md) (the host script installs one more kind of input: an update file the box hands over; box and script exchange more fixed keys), [0024](0024-offline-mode-and-the-one-door-to-the-outside.md) (the way to bring an update to an offline box is a page, not only a guide)

## Context

In offline mode the box does not update itself (ADR 0024). The product owner decided (Q154, 17/11/2026) that a parent can bring an update without internet by **uploading a file** on a settings page, not only by USB stick and command. The preview was approved on 23/11/2026, including installing at once after the parent's confirmation, and the signature check inside the box with sigstore-go (make-or-buy decision, recorded on #221).

## Decision

- **The update file** is `hejmo-<version>-<arch>.update` (arm64 or amd64), a plain tar of three members the release workflow builds for every published version: `hejmo-update.json` (the manifest: format, version, architecture, release date, SHA-256 and size of the image), `hejmo-update.sigstore.json` (the keyless cosign bundle of the release workflow, signing the manifest) and `image.tar` (the image of that architecture, `docker save` format). Signing the small manifest and binding the image by its hash keeps the check short on a Raspberry Pi. Pre-releases get no file and are never installed. `tools/mkupdate` builds and checks the files; the workflow checks each with cosign (as the host script will) and with the box's own library before it publishes.
- **The box checks the file** (`internal/update`): tar members (exactly these three, plain files), manifest, the signature, then published version, architecture, newer than what runs, and the image hash. The signature is checked **offline with `github.com/sigstore/sigstore-go`** (Apache-2.0; product owner's make-or-buy decision) against the Sigstore public-good trusted root that is embedded in the box (`internal/update/trusted_root.json`, fetched with `tools/trustedroot` through the library's own TUF client): the certificate chain to Fulcio, the signed certificate timestamp, the transparency log (Rekor) entry and the signature, with the identity `https://github.com/hejmo-home/hejmo/.github/workflows/release.yml@refs/tags/v<version>` and the issuer `https://token.actions.githubusercontent.com`. Nothing is fetched; the Gate has nothing to refuse. A refused file is deleted at once and the parent gets an error at the field in words.
- **Hand-over.** The box keeps the checked file as `update-file` in the data volume and, after a parent's yes, adds three fixed keys to the settings file: `install=<x.y.z>`, `install_sha256=<64 hex digits>` and `install_time=<RFC 3339>`. The script reads them with exact patterns, never interpolates them, and ignores a request that is older than two hours, from the future or already answered. A systemd path unit (`hejmo-update.path`) runs `hejmo-update --install` when the settings file changes; the nightly run ignores the request.
- **The host script stays the only installer** and does not trust the box: it copies the file out of the data volume (a link is refused), checks the SHA-256 the box named, lists the archive (exactly three members), extracts them into a directory only root reaches, checks the signature again with the cosign image (no network, the same root, kept at `/opt/hejmo/trusted-root.json` by the install script, a test keeps both copies equal), the architecture, the version and the image's hash, loads the image and then does what the nightly update does: backup, switch, health check, rollback. It reports `state=installing` with `step=verify|backup|start|health` and `backup=<time>` in the status file, and the usual final states with the new reasons `file_invalid`, `load_failed` and `verifier_missing`. The install script fetches the cosign image while there is internet, because an offline box cannot.
- **One file at a time** for the whole box (table `update_upload`): a checked file waits at most an hour for the yes; one that is being installed and reports nothing for two hours is given up. Parents only, HTTPS only, only while the host script is told to stay offline, at most 500 MB, and room for two copies of the file and the backup is checked first.
- **Capability flag.** The install script sets `HEJMO_HOST_UPDATER_INSTALL=1` next to `HEJMO_HOST_UPDATER=1`; without it (an updater from before this ADR) the page says the updater is too old and the box offers no upload, because that updater would never act on the request.
- **Installing at once, not at night:** the parent is in front of the page. The page shows the steps in words and loads itself again when the box is back. There is no way back to an older version (migrations).
- **API** (ADR 0015 parity): `GET`, `POST` and `DELETE /update/file`, `POST /update/file/install`.
- **The version the box runs** is known only to the host script. It now records it in the status file on every run, also while offline, so that the page can name what a file replaces.

## Consequences

- A new dependency, `sigstore-go`, and its tree (protobuf specs, Rekor and TUF client packages) are in the binary; its network-capable packages are not used, and the Gate's check (`internal/outbound/bypass_test.go`) still allows no connection outside the Gate.
- The trusted root must be refreshed when the Sigstore project rotates its keys: a test fails when the two copies differ, the release pipeline fails when a root no longer verifies a fresh signature, and an older box needs the new release, which is signed by the new keys but is also what such a box cannot yet check. The remedy for a box that cannot check a new release is the manual way of the install guide.
- The threat model has four new entries (T31 to T34).
